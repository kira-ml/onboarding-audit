# Learning Guide — How to Explain and Defend Onboarding Audit

**Status:** Supporting learning document for v0.2.1 (2026-11-20).
**Purpose:** A plain-English path to understanding the flagship project, so you
can explain its value in a fintech interview, a portfolio review, or a
risk-committee conversation.
**How to use:** Read the one-page summary first. Then work through the concept
map, practice set, feedback loop, and self-test. Do not memorize numbers before
you can explain the mechanism.

---

## 1. Concept map

### 1.1 The one-sentence version

> A bank's current onboarding policy decides which applications get labeled, so a
> normal backtest is biased; this project builds the measurement layer that says
> what a bank can honestly conclude about a new policy — and what it cannot.

### 1.2 First principles: the irreducible facts

Start with facts that do not depend on a model or a library:

1. **A decision is a choice among actions with costs.** The actions are approve,
   review, or reject. Each has a cost: fraud loss, review cost, or false-reject
   (inclusion) cost.
2. **A rejected applicant never becomes a customer.** Their fraud outcome is
   never observed. This is structural, not a data-cleaning problem.
3. **A label is a measurement chosen by the current policy.** Reviewed
   applications get a fast label; approved applications are labeled late, if at
   all; rejected applications get nothing. The labeled sample is selected.
4. **A policy comparison is a counterfactual.** You cannot see what would have
   happened to the same applicant under a different action. You need overlap and
   a credible observation mechanism to estimate it.
5. **The cost matrix is a value judgment.** It is not in the data. A different
   false-reject cost can change the ranking.
6. **The full-population value is not point-identified from logs alone.** The
   reject margin is missing. The honest output is a bound, not a point estimate.
7. **An audit can create random labels for the approved margin.** A random
   post-hoc verification of approved applications does not change the decision,
   so it is defensible. It cannot create labels for rejected applicants.

### 1.3 The first-principles chain

This is the argument to memorize, because it is the spine of every answer:

```
Fact: the current policy chooses who is reviewed, approved, or rejected.
  -> Therefore the labels are not a random sample.
  -> Therefore the naive mean on labeled rows is a different estimand.
  -> Therefore the naive comparison can rank the better policy lower.
  -> Therefore we need an observation model and overlap.
  -> Therefore the identifiable part is P0 (non-rejected), not the full population.
  -> Therefore the reject margin needs bounds or a controlled design.
  -> Therefore an audit of approved applications is the practical identification device.
```

### 1.5 Key invariants

These must remain true in any explanation or implementation:

1. **No label leakage.** The policy and the features are pre-decision. The
   evaluation label is never an input.
2. **Positivity on `P0`.** Every non-rejected row must have a positive chance of
   being observed. If not, no point estimate.
3. **Capacity is real.** The review count cannot exceed the review budget.
4. **The audit is post-approval only.** No random approvals or rejections.
5. **Bounds are not confidence intervals.** They are partial-identification
   intervals conditional on the `P0` estimate.
6. **Claims trace to artifacts.** Every public number comes from a committed
   JSON or a cited source, and appears in the claim ledger.
7. **The correction must match the observation mechanism.** Action-level `e` for
   action-dependent observation; a covariate model when the chance of a label
   depends on the application; audit-only when the label itself depends on the
   outcome.
8. **The naive estimate is a different estimand, not just a noisy version of the
   right one.** This is why the ranking can flip.

### 1.6 Vocabulary

| Term | Plain meaning |
|---|---|
| **Account opening** | The decision to approve, review, or reject a new bank/e-wallet account. The unit is the application, not a transaction. |
| **Action** | `approve`, `review`, or `reject`. Review is a manual KYC/document/identity check. |
| **`P0`** | The applications the current policy did **not** reject. This is the part the log can identify. |
| **Reject margin** | The value contributed by applications the policy rejected. Their outcome is never observed. |
| **Selective labels** | The labels you see are chosen by the current policy, so they are not a random sample. |
| **Propensity (`e`)** | The chance that a row's outcome is observed, given its action and features. |
| **Positivity** | Every row in `P0` must have `e > 0`. If not, the estimate is not identified. |
| **IPW** | Inverse probability weighting: reweight observed rows by `1/e` so they represent the unobserved rows. |
| **DR** | Doubly robust: an outcome model plus an IPW residual correction. It can work if either model is right. |
| **Audit-only** | The mean cost on a random post-hoc verification sample of approved applications. Unbiased for the approved population, high variance. |
| **Bounds** | A best-case/worst-case interval for the full population, conditional on the `P0` estimate. Not a confidence interval. |
| **ESS** | Effective sample size. A small ESS means a few rows are driving the estimate. |
| **Coverage** | How often the 95% interval contains the truth across replications. A diagnostic, not a guarantee. |
| **Label delay / censoring** | A label that has not arrived by the cutoff is unresolved, not negative. |
| **Covariate propensity** | A model of `P(observed \| action, features)` when the chance of a label depends on the application. |
| **Double robustness** | DR's theoretical property: consistent if either the outcome model or the propensity model is correct. It is not a finite-sample guarantee. |
| **Counterfactual** | What would have happened under a different action. You cannot observe both actions for the same applicant. |
| **Policy value** | The expected cost of a policy on a defined population. The project's primary value is on `P0`. |

## 2. Three sub-skills and the binding constraint

### Sub-skill 1 — Frame the decision and the estimand

You can explain, in plain English:

- what decision the bank is making;
- why the current policy determines which labels exist;
- why the naive backtest answers a different question;
- why `P0` is the identifiable part and the reject margin is not.

**Test:** a 2-minute explanation with no jargon, no numbers, and one concrete
example (the metal-detector analogy below).

### Sub-skill 2 — Reason about identification and estimators

You can explain:

- what a propensity is and why positivity matters;
- when IPW works and when it fails;
- why DR is more robust than IPW, and when DR also fails;
- why audit-only is unbiased but noisy;
- why the bounds are not confidence intervals;
- why outcome-dependent labels break action-only weighting;
- why covariate-dependent observation needs a covariate propensity model.

**Test:** given a log, say what can be estimated, what cannot, and which
estimator you would use.

### Sub-skill 3 — Communicate uncertainty and value

You can explain:

- what is measured, assumed, and unverifiable;
- why the cost matrix is an assumption;
- what the audit buys and what it does not;
- why the project is not a production estimate or a causal deployment claim;
- why a risk committee or auditor should care.

**Test:** a one-page memo and a 5-minute Q&A with a skeptical reviewer.

### The binding constraint

**Your binding constraint is feedback on the translation, not more knowledge.**

You already have the code, the results, the claim ledger, and the documentation.
The risk is not that you lack information. The risk is that you can *recognize*
the ideas but cannot *produce* them under pressure — in a 2-minute answer, in a
whiteboard explanation, or when an interviewer interrupts with "why?"

The constraint is a feedback loop with someone who thinks like a fintech
interviewer: a practitioner, a researcher, or a strong peer who will ask "what
would you need to believe?" and "where does this break?"

If you cannot get a person, the next-best constraint is **retrieval practice**:
explain from memory, record it, compare against the canonical docs, and fix one
sentence at a time.

## 3. Practice set, ordered by difficulty

Do not read the answers first. Say the answer out loud, then check the "good
answer must contain" bullets.

### Level 1 — Recall

**Q1. What are the three actions, and what is the unit of analysis?**
- Good answer: approve, review, reject; the unit is a new account application,
  not a transaction.

**Q2. What is `P0`, and why is it the primary estimand?**
- Good answer: the applications the current policy did not reject; it is the part
  the log can identify under positivity and no unmeasured confounding. The
  rejected population has no outcome.

**Q3. What is a propensity, and why does positivity matter?**
- Good answer: the chance a row's outcome is observed given its action and
  features; if `e=0` for a row in `P0`, no reweighting can represent it.

**Q4. Why is a rejected applicant's outcome missing?**
- Good answer: they never become a customer, so there is no account activity,
  chargeback, or fraud report to observe. It is structural missingness, not a
  data-cleaning bug.

### Level 2 — Explain

**Q5. Why does the naive estimate overstate cost and flip the ranking?**
- Good answer: the labeled sample is dominated by reviewed/rejected rows with
  non-zero costs, and approved fraud is more likely to be labeled than approved
  legitimate behavior. The naive mean is a different estimand; it can put the
  incumbent ahead of the better model.

**Q6. Why is audit-only unbiased but high variance?**
- Good answer: the audit is a random sample of approved applications, so its mean
  is unbiased for the approved population; but at a 1% audit the sample is small
  (about 1,271 effective rows), so the interval is wide.

**Q7. Why are the bounds not confidence intervals?**
- Good answer: they are partial-identification intervals conditional on the `P0`
  estimate; the unobserved reject margin is bounded by the cost model, not
  sampled. The incumbent's narrow interval covers the true full value only 34% of
  the time, which is a diagnostic that it is not a 95% CI.

**Q8. Why does DR usually beat IPW? When did DR fail in this project?**
- Good answer: DR adds an outcome model and a residual correction, so it can work
  if either the outcome model or the propensity model is right. It failed under
  covariate-dependent observation with an action-level propensity: 21.25% bias,
  72.5% coverage. The covariate model recovered the oracle.

### Level 3 — Apply

**Q9. A bank has 2% review, 1% audit, a 30-day delay, and no per-row propensity.
What can it estimate? What can't it? What would you recommend?**
- Good answer: estimate `P0` with an estimated action-level propensity; report
  the audit-only estimate for the approved population; do not point-estimate the
  full population; report bounds for the reject margin; check the observation
  rate by amount/segment; if there is a gradient, use the covariate model; size
  the audit to the decision's effect size.

**Q10. The candidate policy reviews 10% of applications, but the incumbent
reviewed 2%. What is the overlap problem? What would you do?**
- Good answer: the candidate explores regions the incumbent never labeled; the
  log cannot identify those regions without an audit or a model assumption.
  Report the candidate review/approve actions outside `P0`; use shadow scoring or
  an audit; if the overlap is poor, report bounds or a diagnostic, not a point
  estimate.

**Q11. The log shows the approve observation rate rising with credit limit.
Which propensity model do you use, and what diagnostics do you report?**
- Good answer: the covariate propensity model (`--propensity-model covariate`);
  report the feature list, propensity range, ESS, max weight, p99 weight, and the
  observation rate by amount quintile. Do not claim the interval is calibrated
  if the weights are heavy.

### Level 4 — Critique and teach

**Q12. An interviewer says: "This is just reject inference. Why is it a flagship?"**
- Good answer: reject inference is the closest analogue, but it is credit
  scoring, usually without delayed labels, capacity-constrained review, an audit
  design, or a regulatory logging schema. This project is the applied measurement
  layer for account-opening approve/review/reject decisions, with a public
  benchmark and an audit-ready memo. The estimators are standard; the assembly
  and the identification discipline are the contribution.

**Q13. An interviewer says: "It's a simulation on synthetic data. Why should we
care?"**
- Good answer: the simulation is a known-ground-truth test of the evaluation
  method, not a production estimate. It shows the naive method can reverse the
  ranking and that the correction works on the identified population. The next
  step is a bank log; the tool is built to run on one.

**Q14. Draw the concept map from memory and explain it to a non-technical risk
manager.**
- Good answer: the five-step chain in §1.3, plus one analogy (the metal detector)
  and one sentence on what the bank should do.

### 4.2 The three-column check

After every explanation, write:

| What I said | What the artifact says | What I assumed |
|---|---|---|
| The exact sentence | The exact number or claim from the JSON / claim ledger | The unstated assumption |

If the middle column is empty, the claim is not ready. If the third column is
doing the work, say it out loud: "This is an assumption, not a measurement."

### 4.3 The error log

Keep a running log. The point is to change the rule, not just the fact.

| Date | Claim | Error type | Correction | Rule change |
|---|---|---|---|---|
| | | wrong number / wrong scope / wrong mechanism / overclaim / missing limitation | | |

Error types:

- **Wrong number:** the figure is stale or from a different scenario.
- **Wrong scope:** you said "full population" when you meant `P0`.
- **Wrong mechanism:** you said "the naive estimate is noisy" instead of "it is a
  different estimand."
- **Overclaim:** you said "production," "causal," or "proves."
- **Missing limitation:** you forgot the reject margin, the simulation, or the
  cost matrix.

### 4.4 The red-team check

Pick one item from `docs/THREATS.md` and try to break the headline:

- "The simulation is an assumption stack."
- "The oracle propensities are not a production assumption."
- "The covariate model is a logistic approximation."
- "The bounds are not confidence intervals."
- "The audit is not a universal fix."

If you cannot state the counter-case and the response in one minute, you do not
yet own the claim.

### 4.5 The stop rule

If you cannot explain a number without opening the doc, do not use the number in
an interview. Use the qualitative claim instead: "The naive estimate was off by
more than 100% and reversed the ranking." A correct qualitative claim is better
than a wrong precise one.

0 = cannot answer; 1 = partial or vague; 2 = correct mechanism and scope.

1. What decision does the project support, and who is the user?
2. Why is the naive estimate biased? Explain the selection mechanism in three
   sentences.
3. What is `P0`, and why not the full population?
4. What are the two identification conditions for `P0`, and what breaks them?
5. When does IPW fail? When does DR fail? Give the project's evidence.
6. Why is audit-only unbiased but noisy? What population does it target?
7. Why are the bounds not confidence intervals? What does the 34% mean?
8. What does the audit buy, and what does it not buy?
9. What is the strongest counter-case, and what is your response?
10. If an interviewer says "just use AUPRC" or "this is reject inference," what

## 6. One-page summary in plain English

Banks and e-wallets must decide whether to approve, review, or reject each new
account. The current policy decides which applications get a fast manual review
and which are approved and only sometimes labeled later. Rejected applicants are
never observed. So the data a bank uses to test a new policy was selected by the
old policy. A normal backtest on the labeled data is therefore biased: in our
simulation it overstated cost by **112–278%** and ranked the better model below
the incumbent.

This project builds the measurement layer that makes the comparison defensible.
It separates the part of the population the log can identify — applications the
current policy did not reject, `P0` — from the part it cannot: the reject margin.
It implements and tests naive, inverse-probability-weighted, doubly robust,
audit-only, and bounds estimators on the public BAF account-opening benchmark. It
designs a compliant audit — random post-hoc verification of approved applications
and shadow scoring, not random approvals or rejections — and produces an
audit-ready memo that separates measured, assumed, and unverifiable claims.

The headline result: doubly robust estimation recovers the identified policy
value within **0.94%** with **96%** coverage, while the naive estimate is off by
more than 100% and would reject the better model. The audit is not a universal
fix: at a 5% approved-label base rate it mainly validates the approved margin,
but it becomes the only approximately unbiased option when approved fraud is more
likely to be labeled than approved legitimate accounts (with an interval that is
still undercovered). The reject margin is not point-identified; the
honest output is a bounds interval, not a confidence interval.

A second study asks what happens when the propensities are estimated rather than
known. Both survive estimated action-level propensities: DR **1.43%** bias,
**93.5%** coverage; IPW **2.92%**, **92.0%**. DR is better under noise. A third
study asks what happens
when the chance of a label depends on the application. Action-level IPW fails
(**67.52%**), and even DR fails (**21.25%**); a fitted covariate propensity model
recovers the oracle (**1.97–3.68%**). The practical rule is: match the propensity
model to the observation mechanism, and report the weight diagnostics.

The value for a fintech team is not another fraud detector. It is the layer that
tells them whether a fraud policy is actually better, what the number means, what
it does not mean, and what audit would make it defensible. That is the difference
between a model that looks good on a backtest and a decision a risk committee can
defend.

## 7. Why this is valuable for a fintech internship

A fintech team already has people who can train a model. What it needs more of is
people who can answer:

1. **What decision does this model change?** Not "what is the AUC?" but "who gets
   approved, reviewed, or rejected, and at what cost?"
2. **What is identifiable?** Which part of the population can the log actually
   speak to, and which part cannot?
3. **What is the right estimator?** When is a simple mean wrong, when does IPW
   fail, when is DR enough, and when do you need a covariate model or an audit?
4. **What is the audit design?** What can you randomize without harming
   customers or violating the law?
5. **Can you defend the number?** What is measured, assumed, and unverifiable?
   What would change the conclusion?

This project is a concrete answer to all five. It is not a notebook; it has a
schema, a validator, a CLI, a benchmark, a report, and a memo. It is not a
production claim; it is a measurement layer with explicit limits. That combination
is rare and credible.

The strongest interview story is not "I built a fraud model." It is:

> "I found that the naive evaluation would reject the better policy. I built the
> correction, the audit design, and the memo that make the comparison defensible.
> Then I tested where the correction fails: estimated propensities, outcome-
> dependent labels, and covariate-dependent observation. The result is a tool
> that tells a bank what it can and cannot conclude."

## 8. Reasoning check

- **Claim and tier:** The explanation is derived from the project's measured
  simulation results and documented methods. The numbers are measured in a
  simulation on public synthetic data, not in a bank.
- **Strongest counter-case:** The observation mechanism and cost matrix are
  assumptions; a real bank's labels may be more outcome-dependent and its
  propensities may be harder to estimate. The project's value is the method and
  the judgment, not a production estimate.
- **Not verified:** No real Philippine bank log, no production deployment, no
  legal sign-off on the audit design. The covariate model is a logistic
  approximation.
- **Next action:** Practice the 2-minute explanation, take the self-test, and get
  one practitioner to challenge the answer. Record the error and change one
  sentence.
